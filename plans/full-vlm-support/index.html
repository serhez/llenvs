    Full VLM (Vision Language Model) Support¶

    Plan for comprehensive VLM integration across llenvs. This is a follow-up to the basic visual support (ImageContent, Observation.images, API backend image formatting) that ships with the Craftax adapter.

    Prerequisites¶

    This plan assumes the basic visual infrastructure is already in place: - ImageContent dataclass in core/state.py - Observation.images field - ChatMessage.images field with to_dict() (OpenAI format) and to_anthropic_dict() (Anthropic format) - supports_vision on BackendCapabilities - Runner _build_messages() propagating images - API backends (OpenAI, Anthropic, OpenRouter) formatting multimodal messages

    1. vLLM Vision Model Support¶

    File: src/llenvs/inference/backends/vllm.py

    Problem¶

    vLLM supports VLMs (LLaVA, Qwen-VL, InternVL, PaliGemma, Phi-3-Vision, etc.) but requires images passed through multi_modal_data parameter in offline inference, not through message content strings.

    Required Changes¶

    Model detection: Detect whether the loaded model is a VLM. vLLM's LLM class exposes model config. Check for vision-related architectures or use a known VLM model list.

    Image preprocessing: VLMs need images as PIL Images or tensors, not base64 strings. Add a conversion step: 

    # ChatMessage.images (base64 str) → PIL.Image → vLLM multi_modal_data
from PIL import Image
import base64, io

def _decode_image(img: ImageContent) -> Image.Image:
    raw = base64.b64decode(img.data)
    return Image.open(io.BytesIO(raw))

    Chat template handling: vLLM's apply_chat_template for VLMs inserts image placeholder tokens (e.g., <image>) that correspond to the multi_modal_data entries. The template application needs to: 1. Count images in the conversation 2. Insert placeholder tokens at the right positions 3. Pass decoded images in multi_modal_data={"image": [pil_img1, pil_img2, ...]}

    Offline inference path (generate()): 

    # Current: llm.generate(prompts, sampling_params)
# VLM:     llm.generate(prompts, sampling_params, multi_modal_data=[{"image": imgs}])

    Chat inference path (generate_chat()): - Extract images from ChatMessage objects - Apply chat template with image placeholders - Pass images via multi_modal_data

    Batch inference: vLLM batches VLM inference automatically. Each prompt in the batch can have different images.

    Set supports_vision=True when a VLM is detected.

    Testing¶

    • Mock vLLM's LLM class with vision model config
    • Test image extraction from ChatMessage → PIL conversion
    • Test prompt construction with image placeholders
    • Test batch inference with mixed text-only and multimodal prompts

    2. HuggingFace Vision Model Support¶

    File: src/llenvs/inference/backends/huggingface.py

    Problem¶

    The current HF backend uses AutoModelForCausalLM and AutoTokenizer, which are text-only. VLMs need AutoProcessor (which combines tokenizer + image processor) and vision-capable model classes.

    Required Changes¶

    Model loading: Detect VLMs and use appropriate classes: 

    # Text-only (current):
tokenizer = AutoTokenizer.from_pretrained(model_path)
model = AutoModelForCausalLM.from_pretrained(model_path)

# VLM:
processor = AutoProcessor.from_pretrained(model_path)
model = AutoModelForVision2Seq.from_pretrained(model_path)
# or: model = LlavaForConditionalGeneration.from_pretrained(model_path)

    Detection options: - Check config.model_type for known VLM types ("llava", "paligemma", "qwen2_vl", etc.) - Check if AutoProcessor returns a processor with an image_processor attribute

    Message formatting: VLMs use processor.apply_chat_template() with image objects: 

    messages = [
    {"role": "user", "content": [
        {"type": "text", "text": "What's in this image?"},
        {"type": "image"},  # placeholder
    ]}
]
inputs = processor(text=prompt, images=[pil_image], return_tensors="pt")

    Generation: Use model.generate(**inputs) where inputs include both text tokens and processed image tensors.

    Batch inference: More complex — need to pad both text and image inputs. The processor handles this with padding=True.

    Set supports_vision=True when a VLM is detected.

    Testing¶

    • Mock HF model/processor classes
    • Test VLM detection logic
    • Test image preprocessing pipeline
    • Test generation with multimodal inputs

    3. Memory Management for Image Trajectories¶

    Problem¶

    Multi-turn trajectories with images per step can consume enormous memory. A 1000-step trajectory with 256x256 PNG images (~50KB each as base64 ~67KB) = ~67MB per trajectory. For Craftax at 100K steps, this is impractical.

    Solutions¶

    3a. Image history truncation on runner (evaluation/runner.py): Add max_image_history: int | None = None parameter to TrajectoryRunner: - When set, only the most recent N images are included in the message history - Older images are replaced with text placeholders: "[Image from step X omitted]" - None = keep all (default, backward compatible)

    3b. Image resolution control on environments: Environments that produce images should accept a image_resolution or image_quality parameter: - Lower resolution = smaller base64 strings - JPEG instead of PNG for lossy compression (~10x smaller) - Let environments decide defaults; users can override

    3c. Logging image stripping (evaluation/logging.py): Add strip_images: bool = False to LogConfig: - When True, images are stripped from trajectory events before logging to JSONL/wandb - Replaced with metadata: {"image_stripped": True, "original_size_bytes": N} - Console logging always strips (just shows "[Image: 50KB PNG]")

    3d. Trajectory storage: Trajectory stores State objects containing Observation. Add an option to strip images when storing trajectories for later analysis: 

    trajectory.strip_images()  # Returns new Trajectory with images removed

    4. DatasetProvider for VLM Tasks¶

    File: src/llenvs/integrations/dataset.py

    Problem¶

    DatasetProvider currently yields TaskItem(prompt=str, ground_truth=str). VLM datasets need to include images.

    Changes¶

    Extend TaskItem: 

    @dataclass(frozen=True)
class TaskItem:
    prompt: str
    ground_truth: str | None
    images: tuple[ImageContent, ...] = ()  # NEW
    metadata: dict[str, Any] = field(default_factory=dict)

    DatasetProvider.__iter__(): Extract images from Observation.images during iteration.

    to_hf_dataset(): Include image data as a column (PIL Images or base64 strings depending on HF datasets conventions).

    5. Gymnasium PixelObservationMapper¶

    File: src/llenvs/adapters/gymnasium.py

    Problem¶

    AutoObservationMapper rejects 2D+ Box observations (images). With ImageContent available, we can support image observations from gymnasium environments.

    Design¶

    class ImageObservationMapper:
    """Renders gymnasium pixel observations as ImageContent.

    Converts numpy RGB arrays to base64-encoded PNG images
    and attaches them to the Observation.

    Args:
        text_description: Optional text to accompany the image.
        format: Image format ("png" or "jpeg").
        quality: JPEG quality (1-100), only used for JPEG.
    """
    def map(self, obs: np.ndarray, info: dict) -> tuple[str, tuple[ImageContent, ...]]:
        # Encode numpy array as image
        # Return (text_description, (ImageContent(...),))
        ...

    def describe(self) -> str:
        return "Visual observation rendered as an image."

    This requires the GymnasiumEnvironment to support mappers that return both text and images. The current ObservationMapper.map() returns str. Options: 1. New protocol MultimodalObservationMapper with map() -> tuple[str, tuple[ImageContent, ...]] 2. Extend existing protocol return type (breaking change) 3. Separate ImageMapper alongside the text ObservationMapper

    Recommendation: Option 1 — new protocol, checked via isinstance. Existing text-only mappers continue to work unchanged.

    Unlocks: Atari (210x160x3), MiniGrid (grid rendering), DMControl (camera), Gym4Real visual modes, any Gymnasium env with pixel observations.

    6. Implementation Order¶

    1. vLLM VLM support — highest impact, enables local VLM evaluation
    2. HuggingFace VLM support — similar to vLLM, enables smaller local VLMs
    3. Memory management — practical necessity for multi-turn visual environments
    4. Gymnasium ImageObservationMapper — unlocks many existing environments
    5. DatasetProvider images — enables VLM dataset construction

    Each item is independent and can be implemented separately.

    7. Testing Strategy¶

    • vLLM: Mock VLM model + processor, test image extraction and prompt construction
    • HuggingFace: Mock AutoProcessor + vision model, test multimodal generation
    • Memory: Test image truncation, logging stripping, trajectory storage
    • Gymnasium: Test ImageObservationMapper with synthetic numpy arrays
    • DatasetProvider: Test TaskItem with images, HF dataset export
